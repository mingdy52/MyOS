# MyOS

> 노션(Notion)에 흩어진 내 일상 기록을 **자연어로 묻고, 답을 받고, 매주 자동으로 회고 리포트를 받아보는** 개인 비서 에이전트.

"이번 달 식비 얼마야?", "지난주 운동 목표 달성률 분석해줘"처럼 한국어로 물으면 끝입니다.
Claude가 **어떤 노션 DB를 어떤 기간으로 조회할지 스스로 판단해(tool use)** 데이터를 모으고 분석해 답합니다.
조회뿐 아니라 새 기록 추가·수정·삭제, 그리고 **주간 회고 리포트 자동 생성**까지 합니다.

```text
질문> 지난주 운동 목표 달성률 분석해줘

🤖 모델: Sonnet · 복잡 분석
🔧 get_targets(...)
🔧 get_workouts({"from":"2026-06-02","to":"2026-06-08"})

주 3회 목표 중 2회 달성(약 67%).
화·목 운동은 꾸준했지만 주말이 비었어요...
```

<br>


### 1. 비용 — 질문 난이도에 따라 모델을 고른다

모든 질문을 상위 모델로 처리하면, "오늘 체중 알려줘" 같은 단순 조회에도 비싼 값을 치릅니다.
그래서 질문의 키워드(`분석` `비교` `달성률` `왜` `추천` …)를 보고 **추가 API 호출 없이** 모델을 결정합니다.

| 질문 유형 | 사용 모델 |
| --- | --- |
| 단순 조회 | **Haiku** — 싸고 빠름 |
| 분석·추론 | **Sonnet** — 상위 모델 |

> **한계** — 키워드 매칭이라 힌트 단어가 없는 복합 질문은 Haiku로 갑니다. LLM으로 판정하면 정확하지만 그 비용이 절감액을 갉아먹어, 비용 0인 규칙 방식을 택했습니다. 규칙은 [`model-router.ts`](src/model-router.ts)에 있고 [테스트](src/model-router.test.ts)로 지킵니다.

여기에 **prompt caching**을 더했습니다.
시스템 프롬프트·도구 정의·대화 기록은 매 호출마다 똑같이 들어가므로, 캐시 브레이크포인트를 걸어 **두 번째 호출부터는 정가의 ~10%로 재사용**합니다.
매 응답마다 토큰 사용량(입력 / 출력 / 캐시 읽기 / 캐시 쓰기)을 출력해, 캐싱이 실제로 먹히는지 눈으로 확인하며 만들었습니다.

### 2. 유지보수 — DB를 노션에서 자동 발견하는 스키마 주도 설계

DB를 하나 추가할 때마다 데이터소스 id를 `.env`에 적고, 조회·쓰기 코드와 도구 설명을 일일이 고치는 건 비효율적입니다.
그래서 **모든 DB가 들어있는 부모 페이지 하나**만 알려주면, 앱이 시작할 때 그 페이지를 훑어 안의 DB들(데이터소스 id·컬럼·타입)을 **자동으로 발견**하고 캐시에 저장합니다. 읽기·쓰기·도구 설명문은 모두 이 발견된 스키마를 바라봅니다.

> 새 DB는 **노션에서 만들고 `refresh` 한 번**이면 끝 — 코드·설정을 한 줄도 안 고칩니다.

- **캐시 우선** — 평소엔 캐시만 읽어 네트워크 호출 0. 노션에서 DB·컬럼을 바꿨을 때만 `refresh`로 다시 훑습니다.
- **본문형 표시** — 제목이 `+`로 끝나는 DB(일기·알고리즘 로그 등)는 "페이지 본문에 자유 서술을 적는 DB"로 인식해, 조회 시 본문까지 함께 읽어옵니다.
- **단일 조회 진입점** — 모든 읽기는 `getRecords(db, { 기간·필터·본문 })` 하나로 처리해, DB마다 리더 파일을 두지 않습니다.

### 3. 운영 — 안전한 쓰기와 무인 자동화

- **쓰기 가드레일** — 조회는 마음껏 하되, 데이터를 바꾸는 추가·수정·삭제는 실행 직전에 "무엇을 → 어떤 값으로" 바꿀지 보여주고 `y/N` 확인을 받습니다. 수정 시에는 기존 값을 읽어와 `기존 → 새값`으로 대조해 줍니다.
- **주간 리포트 자동화** — GitHub Actions가 매주 월요일 오전 9시(KST)에 전주(지난주 월~일) 데이터를 모아 Claude에게 분석을 받고, 노션 "리포트" DB에 회고 페이지로 저장합니다. 사람 개입이 없는 1회성 배치라 REPL과 코드 경로를 분리했습니다.
- **"말과 행동의 차이"는 의사결정 로그로 대조합니다** — 리포트의 이 섹션은 원래 감정지표만 보고 다짐을 추측했습니다(속도 때문에 일기 본문을 읽지 않으므로). 지금은 *하기로 한 것*(의사결정 로그)과 *실제 한 것*(운동·공부·지출·지원 기록)을 직접 맞춥니다. 예를 들어 "기회 있을 때 바로 지원하기"라는 결정이 그 주 지원 0건과 대조돼 잡힙니다 — 지원 현황 DB를 안 읽던 때는 구조적으로 불가능하던 지적입니다.

### 4. 확장 — 오케스트레이터 + 도메인 에이전트

기록이 쌓이자 관심이 "저장·조회"에서 "그래서 뭘 할까"로 옮겨갔습니다. 기분이 가라앉은 날 볼 만한 영상을 골라 주는 일 같은 건, 지금까지의 노션 도구와 성격이 다릅니다 — **내 데이터를 다루는 게 아니라 바깥 콘텐츠를 다루기** 때문입니다.

그래서 에이전트를 도메인별로 나누되, 서로 직접 대화하지 않고 **하나의 오케스트레이터가 조율**하는 구조로 갔습니다.

```text
              사용자
                │
              사용자
                │
        Personal Agent  ← 오케스트레이터 (기록을 읽고 판단, 기억을 관리)
        ├── 노션 도구 (조회·추가·수정·삭제)
        ├── 장기 기억 (대화·재시작을 넘어 남는 사용자 맥락)
        ├── Reflection Agent ← 회고 담당 (일기 정독·결정 추출·패턴 분석)
        └── Media Agent      ← 콘텐츠 담당 (유튜브 검색·보관함·감정별 추천)
```

세 에이전트는 **보는 곳이 다릅니다.** Reflection은 *가장 사적인 기록*(일기)만, Media는 *바깥 세상*(유튜브)만, Personal은 그 사이에서 조율합니다.

```text
질문> 요즘 내 감정 패턴이 어떤지 봐줘

🔧 get_diaries({"from":"2026-07-01","to":"2026-07-29"})        ← 감정지표만 가볍게
🔧 reflection_agent({"request":"7월 일기 분석해서 감정 패턴을 짚어줘. 아래는 이미 조회한 지표…"})
   ↳ reflection_agent에 위임
   │ 🔧 read_diaries({"from":"2026-07-01","to":"2026-07-10"})   ← 본문 정독
   │ 🔧 read_diaries({"from":"2026-07-11","to":"2026-07-20"})
   │ 🔧 read_diaries({"from":"2026-07-21","to":"2026-07-29"})
   ↳ reflection_agent 응답 받음
🔧 remember({"category":"패턴","fact":"가까운 사람과 만난 뒤 기분이 급상승하지만…"})
   🧠 기억했어요
```

오케스트레이터가 가벼운 조회로 밑그림을 잡아 넘기고, 전문 에이전트가 깊게 파고, 돌아온 결론 중 **오래갈 것만 장기 기억에 남깁니다.** 셋이 각자 자기 일만 합니다.

- **무엇을 에이전트로 승격할지** — "코드가 몇 줄이면"이 아니라 세 가지로 판단했습니다. ① *중간 산출물이 최종 답보다 큰가* — 유튜브 검색은 영상 5개의 JSON(약 1천 토큰)을 받아 두세 줄로 요약합니다. 서브에이전트 안에서 그 JSON은 쓰이고 버려지지만, 그냥 도구였다면 대화 기록에 박혀 **이후 모든 질문마다 재전송**됩니다. ② *도구를 격리해야 하는가* — Reflection은 일기·의사결정만, Media는 콘텐츠만 만질 수 있어서 회고하다 가계부를 지우는 일이 구조적으로 불가능합니다. ③ *그 도메인 전용 지시가 오케스트레이터 프롬프트를 잠식하는가* — 일기 해석 요령이 Personal 시스템 프롬프트의 23%(73줄 중 17줄)를 차지하고 있었고, "이번 달 식비 얼마야?"에도 매번 실려 갔습니다. Reflection을 분리한 직접적인 이유가 이것입니다.
- **도구와 에이전트의 구분** — 노션 조회는 "시키는 대로 한 가지 일만 하는" 도구입니다. 반면 회고나 콘텐츠 추천은 *어디서 찾을지·무슨 기준으로 고를지*를 스스로 정해야 하므로 에이전트로 뒀습니다. 이 기준으로 `tools/`와 `agent/`를 나눴습니다.
- **링크는 지어내지 않는다** — "우울할 때 볼 영상 추천해줘"에 LLM이 그냥 답하면 그럴듯한 유튜브 URL을 만들어내고, 열어보면 404입니다. 그래서 Media Agent가 건네는 링크는 **보관함(노션)이나 유튜브 검색 API 결과에서 나온 것만**으로 제한했습니다. 맞는 게 없으면 지어내는 대신 실제로 검색합니다.
- **저장 자체가 평가다** — 보관함에 `좋아요` 같은 평가 칸을 따로 두지 않았습니다. 좋았던 것만 저장하니 표시가 중복이고, 별로였던 건 꺼두는 게 아니라 지우면 그만입니다. 덕분에 조회 로직에 정렬·필터가 하나씩 줄었습니다.
- **라우터를 따로 두지 않음** — intent를 분류해 분기하는 Router 클래스를 만드는 대신, **서브에이전트를 도구 하나로 노출**했습니다. Claude가 매 턴 "어떤 도구를 부를까"를 이미 고르고 있으므로 그 선택이 그대로 라우팅이 됩니다. 규칙표를 사람이 관리할 필요가 없고, 새 도메인을 붙이는 비용은 *규격을 만족하는 객체 하나 + 배열에 한 줄*입니다.
- **맥락은 위에서 아래로만** — Media Agent는 사용자의 일기를 볼 수 없습니다. "왜 이런 감정인지"는 Personal Agent가 파악해 요청 문장에 담아 넘기고, Media Agent는 "이 감정이면 이런 콘텐츠"만 잘하면 됩니다. 각자 자기 역할만 알기 때문에 서브에이전트가 늘어도 서로 얽히지 않습니다.
- **엔진은 하나** — 도구 루프·prompt caching·토큰 집계·쓰기 확인은 [`agent/core.ts`](src/agent/core.ts) 하나에 있고 모든 에이전트가 공유합니다. 도메인 지식은 각 에이전트 파일에만 둡니다. 위임해서 쓴 토큰도 같은 집계에 쌓여 "이번 질문 비용"이 그대로 보입니다.

### 5. 기억 — 매번 처음부터 알아내지 않기

"월요일마다 방전된다"는 걸 알아내려면 일기 2주치를 읽어야 합니다. 문제는 다음에 물어도 **또 2주치를 읽는다**는 것이었습니다. 한 번 알아낸 사실은 계속 참인데도요.

그래서 대화를 넘어 남는 **장기 기억**을 뒀습니다. 기록을 가로질러 결론을 낸 직후에 비서가 스스로 적습니다.

```text
🔧 get_diary_details({"from":"2026-07-15","to":"2026-07-29"})
🔧 remember({"category":"패턴","fact":"주말에 일하고 나면 월요일마다 방전되어..."})
   🧠 기억했어요 — [패턴] 주말에 일하고 나면 월요일마다 방전되어...
```

- **기억과 조회의 역할을 갈랐습니다** — 기억은 *어떤 사람인지*(반복되는 패턴·취향·목표), 노션 조회는 *지금 값이 얼마인지*(이번 주 지출, 어제 운동). 그래서 "이번 달 식비" 같은 건 기억에 뭐가 있든 항상 새로 조회합니다. 기억이 노션의 낡은 복사본이 되면 오히려 해롭습니다.
- **캐시를 깨지 않는 자리에 넣었습니다** — 기억은 시스템 프롬프트의 *캐시 블록 뒤*, 날짜와 같은 칸에 실립니다. 앞에 넣으면 기억이 하나 늘 때마다 큰 캐시가 통째로 무효가 됩니다.
- **도구를 준다고 쓰지는 않습니다** — 처음엔 "알게 되면 적어라"로 뒀더니 분석만 잘 해놓고 한 번도 안 적었습니다. *언제* 부를지(기록을 가로질러 결론을 낸 직후)를 시스템 프롬프트와 도구 설명 양쪽에 못 박고 나서야 동작했습니다.
- **비서의 수첩이라 y/N을 묻지 않습니다** — 쓰기 확인은 사용자의 진짜 노션 데이터를 지키는 장치입니다. 기억은 로컬 파일이고 되돌리기 쉬워서, 확인 대신 무엇을 적었는지 화면에 보여주는 쪽을 택했습니다. `memory` 명령으로 언제든 전부 확인할 수 있습니다.

## 기술 스택

Node.js (ESM) · TypeScript (strict) · [`@anthropic-ai/sdk`](https://www.npmjs.com/package/@anthropic-ai/sdk) (Claude tool use) · [`@notionhq/client`](https://www.npmjs.com/package/@notionhq/client) · GitHub Actions · [`node:test`](https://nodejs.org/api/test.html)

> strict로 켜 두었지만, 노션 SDK 응답은 경계에서 `any`로 받아 `props.ts`에서 우리 타입으로 파싱합니다. 내부 로직은 그 뒤의 좁혀진 타입 위에서 돕니다.

## 테스트

부작용 없는 순수 로직을 별도 모듈로 분리해 [`node:test`](https://nodejs.org/api/test.html)로 검증합니다 — 추가 의존성·키 없이 돕니다.

- [`model-router.ts`](src/model-router.ts) — 모델 라우팅 규칙
- [`notion/filters.ts`](src/notion/filters.ts) — 노션 필터 조각 생성
- [`youtube.ts`](src/youtube.ts) — 유튜브 기간 문자열(`PT4M13S`) 파싱

```bash
npm test   # *.test.ts (21개)
```

> 노션 실연동은 키가 필요해 수동으로 검증합니다. push·PR마다 CI가 `tsc --noEmit`와 `npm test`를 돌립니다.

## 구조

```text
src/
├── index.ts             # 대화형(REPL) 껍데기 — 명령 파싱 후 ask()에 위임
├── agent/
│   ├── types.ts         # 공용 규격 — 도구(ToolDef)·에이전트(Agent)·실행 맥락
│   ├── core.ts          # 도구 루프 엔진 — 캐싱·토큰 집계·쓰기 확인·위임 어댑터 (도메인 무관)
│   ├── personal.ts      # Personal Agent(오케스트레이터) — 사용자와 대화, 기억 관리, 위임
│   ├── reflection.ts    # Reflection Agent — 일기 정독·결정 추출·감정 패턴 분석
│   └── media.ts         # Media Agent — 감정에 맞는 콘텐츠 검색·저장·추천
├── tools/
│   ├── notion.ts        # 노션 도구 — 조회 12종 + 추가·수정·삭제

│   ├── reflection.ts    # 회고 도구 — 일기·의사결정 조회 + 결정 기록
│   └── media.ts         # 콘텐츠 도구 — 유튜브 검색 + 보관함 조회·저장·삭제
├── memory.ts            # 장기 기억 저장소 (data/memory.json, 대화·재시작을 넘어 유지)
├── youtube.ts           # 유튜브 데이터 API — 실제 존재하는 영상 검색 (환각 방지)
├── youtube.test.ts      # ↑ 기간 문자열 파싱 단위 테스트
├── model-router.ts      # 질문 → 모델(Haiku/Sonnet) 라우팅 규칙 (순수·테스트 대상)
├── model-router.test.ts # ↑ 라우팅 규칙 단위 테스트
├── report.ts            # 주간 리포트 배치 (스케줄러용)
├── portfolio-draft.ts   # 포트폴리오 초안 생성 (노션 → 검수용 JSON, 수동 실행)
├── site.ts              # 검수된 JSON → 정적 HTML 빌드 (GitHub Pages 배포)
├── content/             # 검수·확정된 포트폴리오 콘텐츠 (JSON)
└── notion/
    ├── discover.ts      # 부모 페이지 → 안의 DB들(데이터소스·컬럼) 자동 발견
    ├── schema-sync.ts   # 발견 결과를 스키마에 반영 (캐시 우선, refresh로 갱신)
    ├── schema-cache.ts  # 발견 결과 캐시 (.cache/notion-schema.json)
    ├── schema.ts        # DB 스키마(역할·제목·컬럼) — 발견 실패 시 fallback seed
    ├── query.ts         # 공통 조회 — getRecords 단일 진입점 (기간·필터·본문)
    ├── filters.ts       # 노션 필터 조각 생성 (순수·테스트 대상)
    ├── filters.test.ts  # ↑ 필터 생성 단위 테스트
    ├── props.ts         # 속성 파싱
    ├── mutate.ts        # 추가·수정·삭제
    ├── blocks.ts        # 페이지 본문(블록) 텍스트 읽기
    └── render.ts        # 노션 페이지 본문 → HTML 변환
```

## 실행

```bash
npm install
cp .env.example .env   # ANTHROPIC_API_KEY, NOTION_API_KEY, NOTION_DATA_PAGE_ID
                       # (선택) YOUTUBE_API_KEY — 영상 검색용, 없으면 보관함만 사용

npm run dev            # 대화형 비서 (REPL 명령어: help / db / memory / refresh / token / clear / exit)
npm run report         # 주간 리포트 수동 생성
npm run portfolio      # 포트폴리오 콘텐츠 초안 생성 (노션 → 검수용 JSON)
npm run site           # 검수된 JSON → 정적 HTML 빌드 (GitHub Pages 배포물)
```
